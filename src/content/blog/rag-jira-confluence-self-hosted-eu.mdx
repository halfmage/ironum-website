Your team's knowledge is split between two places. Jira holds what was decided, issue by
issue, mostly in the comments. Confluence holds why: the specs, the architecture notes, the
retrospectives. Asking a question that needs both, such as "why did we drop offline mode
for the mobile app, and is anything still open on it?", means an hour of searching.

A retrieval system can answer it in seconds, with a link to every issue and page it used,
and without showing anyone content they could not open in Jira or Confluence. This article
explains how RAG over Jira and Confluence works when it runs on infrastructure you control
in the EU, where it beats an off-the-shelf connector, and where it does not.

## Key Takeaways

- **RAG** means the model answers from passages retrieved from your own Jira and Confluence at question time, and cites them. Nothing is trained on your data.
- Microsoft's Copilot connectors are the simplest option if you run supported Atlassian versions and hold Microsoft 365 Copilot add-on licenses. A self-hosted system fits when you need comments, Jira Server, a non-Microsoft index, or your own choice of model and hosting.
- The hard parts are not the model. They are **permissions**, **freshness** and **citations**.
- Hosting can be your own servers or an EU cloud provider, with an open-source model, so the content does not leave infrastructure you choose.

## Copilot Connector or Self-Hosted RAG?

Start with the honest comparison. If the connector covers your case, use it.

| Question | Microsoft 365 Copilot connectors | Self-hosted RAG |
|---|---|---|
| Jira Cloud | Supported | Supported |
| Jira Data Center | Separate connector, on-premises agent and plugin | Supported via API |
| Jira Server | Not supported | Supported via API |
| Jira comments | Not listed for Jira Cloud; on request for Data Center | Indexed if you choose |
| License to use it in answers | Microsoft 365 Copilot add-on or E7 | Your own infrastructure cost |
| Where the index lives | Microsoft 365 | Where you deploy it |
| Choice of model | Microsoft's | Yours, including open-source |

## How RAG Over Jira and Confluence Works

If RAG is new to you, [enterprise RAG explained](/resources/blog/enterprise-rag-explained/)
covers the idea without the technical detail. Here is how it applies to Jira and Confluence.

**1. Ingestion.** A sync service reads issues, comments, attachments and pages through the
Jira and Confluence REST APIs, with a service account that has read access to the projects
and spaces in scope. You decide the scope: all projects, or only the ones a pilot team uses.

**2. Chunking.** Long pages and long comment threads are split into passages small enough
to retrieve precisely. Each passage keeps its source: issue key or page ID, title, author,
date, and a link back.

**3. Embedding and indexing.** Each passage is turned into a vector by an embedding model
(it turns text into numbers that capture meaning, so similar passages end up close
together) and stored in a vector database next to its text and metadata. Both the embedding model and
the database can run on your own servers.

**4. Permission filtering.** Every passage carries the access rules of the item it came
from: Jira project permissions and issue security levels, Confluence space permissions and
page restrictions. When someone asks a question, the search is filtered by that person's
identity before any passage reaches the model. Someone who cannot open an issue in Jira
cannot get an answer built from it.

**5. Retrieval and answer.** The question is embedded, the closest permitted passages are
retrieved, and the language model writes an answer from those passages only, with a
citation for each claim.

**6. Sync.** Content changes are picked up incrementally, typically every few minutes.
Permission changes get their own schedule, because a person removed from a project should
lose access to its content quickly.

## The Three Things That Decide Quality

**Permissions.** This is where most first versions fail. Jira and Confluence permissions
are layered: groups, project roles, issue security levels, space permissions, page
restrictions. Map them carefully and decide what happens when a rule cannot be resolved.
The safe answer, and the one Microsoft's own Data Center connector uses, is to deny access.

**Freshness.** An assistant that answers from yesterday's backlog is worse than none,
because it sounds confident. Measure how long a change takes to appear in answers, and
show the "last updated" date of every cited source.

**Citations.** Every answer should link to the issues and pages it used. It is how users
learn to trust the system, and how they catch it when the retrieval picked the wrong
passage.

## Hosting in the EU

A self-hosted system can run in three ways:

- **On your own servers**, with an open-source model. The content never leaves your network.
- **On dedicated servers at an EU provider**, such as Hetzner or IONOS in Germany, again with an open-source model.
- **In an EU cloud region of a hyperscaler**, if your organization already runs there.

In all three, you choose where the index and the model run and which models are used. That
is a technical choice about where data is processed. Whether a given setup meets your
organization's obligations is a question for your data protection officer.

## How Long a Jira and Confluence RAG Takes to Build

At Ironum, a working proof of concept on a customer's real Jira and Confluence data
typically takes around two weeks: one pilot project, one Confluence space, permission
filtering switched on from day one. A production system typically takes four to eight
weeks, depending on data volume, how complex the permissions are, and where it has to be
integrated, for example as a chat in Teams or a panel inside Jira.

**What we need from you:** read access for a service account, one pilot Jira project and
one Confluence space, and a handful of real questions your team asks every week.

**What you have after about two weeks:** a working assistant on that pilot data,
permission filtering on from day one, cited answers your team can test against what it
already knows, and a plan for production.
